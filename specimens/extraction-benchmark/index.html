SP-04 Runner scoring

extraction-benchmark

Containment class — methodology

A small, rigorous benchmark for structured extraction. Benchmarks get shared and cited, so the credibility has to come from a defensible methodology rather than a leaderboard-topping score.

Headline metric
field-level F1
Regex baseline
0.80 F1
Reported beside it
strict exact match
Normalisation
explicit, documented

Why this exists

A benchmark is only as good as its method. This one is built so a sceptical reader can audit every choice: what counts as correct, what gets normalised before comparison, and what floor a model has to clear before its score means anything.

Out of the box it runs a regex baseline, so the harness produces real numbers immediately rather than waiting on model access — currently 0.80 field F1. A model that cannot beat regex on this task is itself a result worth reporting.

The example task is invoice field extraction. The scaffold is meant to be repointed at a domain you actually know, because the value of a benchmark lives in the quality and realism of its eval set.

What is measured

Field-level F1
The headline metric — partial credit per field, computed from precision and recall over correctly extracted fields.
Exact match
A stricter view reported alongside: did the entire record match? The gap between the two is informative on its own.
Explicit normalisation
Case, whitespace, currency symbols and thousands separators are normalised so “$1,250.00” equals “1250.00”. Documented, because silent normalisation choices are how benchmarks mislead.
A non-trivial baseline
Regex gives every model a floor to beat.

Layout

extraction-benchmark/
├── src/
│   ├── run_benchmark.py   # runs all models, scores, writes the table
│   ├── models.py          # adapters (regex baseline + LLM slots)
│   └── scoring.py         # field-level F1, exact match, normalisation
├── data/
│   └── eval_set.jsonl     # gold-labelled examples, hand-written
└── results/               # versioned result artifacts

Run it

pip install -r requirements.txt
python -m src.run_benchmark --data data/eval_set.jsonl --models all --out results/

Sample output:

model                     field_F1     exact     p50_s
------------------------------------------------------
regex-baseline               0.800     0.000     0.000

Limitations

  • The shipped eval set is 3 illustrative examples. A credible benchmark needs 50+ hand-labelled, realistic cases — generating them with a model defeats the point.
  • Single annotator. For a public benchmark, a second annotator and an inter-annotator agreement number would strengthen it considerably.
  • Exact and normalised matching can be too strict for free-text fields such as vendor names.

What I would do next

  • Expand to 50–100 hand-labelled real documents and report a confidence interval.
  • Add fuzzy matching for name-like fields and report both strict and fuzzy F1.
  • Add cost-per-document so the quality/cost tradeoff across models is visible.
